Bring your assistant into the apps you build.

The My Assistant API connects any app you build — web, mobile, desktop, a bot, a device — to your own assistant from My Assistant. It is the same assistant: it knows you, remembers your conversations and shares one account and one bill. Your app can also give it new abilities that only exist in your app, and everything that happens there flows back, so you can ask My Assistant about it later.

TalkSend text, get the assistant's reply. Threads keep context.
ActDescribe your app's actions; the assistant calls them when the user asks.
SpeakOpen a realtime voice-to-voice session in one call.
RememberSave activity and data; My Assistant can answer questions about it.

Key concepts

TermWhat it means
AccountThe user's My Assistant account. Everything an app does happens as this account: same memory, same history, same usage.
AppOne program you connect, created in the Developer Console. Each app has its own keys, permissions, data and activity feed.
API keyA secret (mya_ + 40 characters) that identifies the app and acts as the user. Shown once when created.
ScopesWhat the app is allowed to do (talk, voice, read memory…). Set in the Console, checked on every request.
ConversationA thread of messages identified by conversation_id. Send it back to continue the thread.
App toolsActions that exist in your app, described to the assistant as functions. The assistant decides when to use them; your code runs them.
Assistant toolsThe assistant's own built-in abilities (reminders, web search, weather, lists…). They run on our side automatically.
EventsOne-line reports of what happened in your app. Shown to the user and searchable by the assistant.
RecordsYour app's own JSON data, stored on the user's account in named collections.

Your UI talks to your backend; your backend calls the API with the key. When the assistant wants to use one of your app's actions, the API returns it to your backend, your backend performs it and sends the result back. For voice, your backend asks for a short-lived voice session and the UI connects to it directly — the key never leaves your server.

Integration guide

Follow the steps in order. Steps 1–4 give you a working chat; 5–7 make the assistant truly part of your app.

Step 1 · Create your app and get a key

  1. Open the Developer Console and sign in with your My Assistant account (a code is sent to your phone).
  2. Click New app. Give it a name and a one-line description, and list the words people use for it — this is how My Assistant knows a question is about your app.
  3. Choose its permissions (scopes). The defaults are fine to start.
  4. Copy the API key. It is shown only once; you can always create another.

The app appears in My Assistant on the phone (Hub → Your own apps) straight away.

Step 2 · Keep the key on your server

The key acts as the user. Store it as an environment variable on your backend and never send it to a browser, a mobile app bundle or a public repository.

# .env on your server
MYA_KEY=mya_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
MYA_API={{API}}
Building only for yourself, on your own machine? Calling the API directly from a local script is fine. The rule is about anything other people can download or inspect.

Step 3 · Send your first message

curl $MYA_API/assistant/messages \
  -H "Authorization: Bearer $MYA_KEY" \
  -H "Content-Type: application/json" \
  -d '{"message": "Hi! What should I focus on today?"}'

Response:

{

  "status": "completed",
  "reply": "Good morning! You have a dentist appointment at 4 pm …",
  "tool_calls": [],

actions lists the assistant's own tools it used while answering. Replies can take a few seconds when it uses tools — use a timeout of about 60 seconds.

Step 4 · Hold a conversation

Save conversation_id from each response and send it with the next message. Without it, each message starts a new thread (the assistant still knows the user and recent history, but not the details of this thread).

{ "message": "Move it to 5 pm instead", "conversation_id": "conv_6f1c2a…" }

Two optional fields shape a conversation:

  • instructions — how the assistant should behave in this conversation, e.g. "Answer in two sentences. You are helping inside a budgeting app."
  • context — what your app shows right now (the open screen, the selected item, current totals), as a string or JSON. It is treated as data, never as instructions.

Step 5 · Let the assistant act in your app (app tools)

This is what makes the assistant more powerful in your app than anywhere else. Describe the actions your app can perform as tools: a name, a description the assistant reads, and the parameters as JSON Schema. When the user's request needs one, the API stops and hands the call to your backend.

The tools below are placeholders — replace them with your app's real actions.

const TOOLS = [
  {
    name: "create_item",
    description: "Create a new item in the user's workspace in this app.",
    parameters: {
      type: "object",
      properties: {
        title: { type: "string", description: "Short title" },
        due:   { type: "string", description: "ISO date, if the user gave one" }
      },
      required: ["title"]
    }
  },
  {
    name: "search_items",
    description: "Find the user's items in this app by text.",
    parameters: { type: "object", properties: { query: { type: "string" } }, required: ["query"] }
  }
];

The loop

1Send message with tools.
2If status is "requires_action", run each call in tool_calls.
3Send all results back as tool_results with the same conversation_id.
4Repeat until status is "completed", then show reply.
const API = process.env.MYA_API, KEY = process.env.MYA_KEY;

async function mya(body) {
  const r = await fetch(`${API}/assistant/messages`, {
    method: "POST",
    headers: { Authorization: `Bearer ${KEY}`, "Content-Type": "application/json" },
    body: JSON.stringify(body),
  });
  const j = await r.json();
  if (!r.ok) throw new Error(j.error.message);
  return j;
}

// Your app's own code: one branch per tool you declared.
async function runTool(name, args, user) {
  switch (name) {
    case "create_item":  return await db.items.create({ owner: user.id, ...args });
    case "search_items": return await db.items.search(user.id, args.query);
    default: throw new Error(`unknown tool ${name}`);
  }
}

export async function ask(user, message, conversationId) {
  let r = await mya({ message, conversation_id: conversationId, tools: TOOLS,
                      context: { screen: user.currentScreen } });
  while (r.status === "requires_action") {
    const tool_results = [];
    for (const call of r.tool_calls) {
      try {
        tool_results.push({ call_id: call.id, output: await runTool(call.name, call.arguments, user) });
      } catch (e) {
        tool_results.push({ call_id: call.id, error: String(e.message || e) });
      }
    }
    r = await mya({ conversation_id: r.conversation_id, tool_results });
  }
  return { reply: r.reply, conversationId: r.conversation_id };
}
import os, requests

API, KEY = os.environ["MYA_API"], os.environ["MYA_KEY"]

def mya(body):
    r = requests.post(f"{API}/assistant/messages", json=body, timeout=60,
                      headers={"Authorization": f"Bearer {KEY}"})
    j = r.json()
    if not r.ok:
        raise RuntimeError(j["error"]["message"])
    return j

# Your app's own code: one branch per tool you declared.
def run_tool(name, args, user):
    if name == "create_item":
        return db.create_item(owner=user.id, **args)
    if name == "search_items":
        return db.search_items(user.id, args["query"])
    raise ValueError(f"unknown tool {name}")

def ask(user, message, conversation_id=None):
    r = mya({"message": message, "conversation_id": conversation_id, "tools": TOOLS,
             "context": {"screen": user.current_screen}})
    while r["status"] == "requires_action":
        results = []
        for call in r["tool_calls"]:
            try:
                results.append({"call_id": call["id"], "output": run_tool(call["name"], call["arguments"], user)})
            except Exception as e:
                results.append({"call_id": call["id"], "error": str(e)})
        r = mya({"conversation_id": r["conversation_id"], "tool_results": results})
    return r["reply"], r["conversation_id"]
  • Answer every call in one tool_results request. output can be a string or any JSON; send error instead when the action failed — the assistant will tell the user honestly.
  • Tools are remembered for the conversation; send tools again only to change them.
  • The assistant may use its own tools in the same turn — those run automatically and appear in actions.
  • Up to 24 app tools. Names: start with a letter; letters, digits, _, -; max 64; not the same as an assistant tool name (the API tells you if it is).
  • Write descriptions for the assistant, in plain words: what the action does and when to use it. Good descriptions are the difference between a tool that gets used and one that doesn't.

Step 6 · Report what happens (so My Assistant knows)

Two ways to make your app's activity part of the user's shared history:

  • Events — one human-readable line per meaningful moment. Shown under your app in My Assistant, and what the assistant searches when the user asks "what happened in <your app>?".
  • Records — structured data you want to keep (results, settings, saved items). Give each a short summary: it's the line the assistant reads.
# An event: something happened
POST {{API}}/events
{ "type": "item_completed", "summary": "Finished the quarterly report draft", "data": { "itemId": "it_42" } }

# A record: data to keep (PUT creates or replaces)
PUT {{API}}/records/items/it_42
{ "summary": "Quarterly report draft — done on 14 Oct", "data": { "status": "done", "words": 2140 } }

Later, in My Assistant: "What did I finish in <your app> this week?" — the assistant answers from these.

Step 7 · Add voice (optional)

For a spoken, real-time conversation, your backend opens a voice session and passes a short-lived secret to the UI, which connects directly to the realtime voice service.

// Your backend
const s = await fetch(`${API}/voice/sessions`, {
  method: "POST",
  headers: { Authorization: `Bearer ${KEY}`, "Content-Type": "application/json" },
  body: JSON.stringify({ tools: TOOLS, instructions: "Keep answers short." }),
}).then(r => r.json());
// → send { client_secret: s.client_secret, connect: s.connect, app_tools: s.app_tools } to the UI
// The browser (WebRTC)
const pc = new RTCPeerConnection();
const audio = new Audio(); audio.autoplay = true;
pc.ontrack = (e) => (audio.srcObject = e.streams[0]);
const mic = await navigator.mediaDevices.getUserMedia({ audio: true });
pc.addTrack(mic.getTracks()[0]);
const events = pc.createDataChannel("oai-events");
const offer = await pc.createOffer();
await pc.setLocalDescription(offer);
const answer = await fetch(session.connect.webrtc, {
  method: "POST", body: offer.sdp,
  headers: { Authorization: `Bearer ${session.client_secret}`, "Content-Type": "application/sdp" },
});
await pc.setRemoteDescription({ type: "answer", sdp: await answer.text() });

// When the assistant calls a tool during the conversation:
events.onmessage = async (m) => {
  const ev = JSON.parse(m.data);
  if (ev.type !== "response.function_call_arguments.done") return;
  const args = JSON.parse(ev.arguments || "{}");
  // Your app's tools run in your app; assistant tools go through your backend
  // to POST /v1/tools/call.
  const output = session.app_tools.includes(ev.name)
    ? await runToolInApp(ev.name, args)
    : await fetch("/api/assistant-tool", { method: "POST", body: JSON.stringify({ name: ev.name, arguments: args }) }).then(r => r.json());
  events.send(JSON.stringify({ type: "conversation.item.create",
    item: { type: "function_call_output", call_id: ev.call_id, output: JSON.stringify(output) } }));
  events.send(JSON.stringify({ type: "response.create" }));
};

When the conversation ends, post the transcript to /v1/voice/transcript so it becomes part of the user's history and the minutes are counted.

Go-live checklist

  • The key is only on your server, read from an environment variable.
  • You store and reuse conversation_id per user thread.
  • Every tool call is answered — with output or error.
  • You handle 429 (slow down / daily limit) and 503 (try again) — see Errors.
  • Your app reports meaningful moments as events, with summaries a person would understand.
  • Only the scopes you need are switched on in the Console.

API reference

Base URL {{API}}. Requests and responses are JSON.

Authentication & scopes

Send the key on every request: Authorization: Bearer mya_… (or X-Api-Key: mya_…). Scopes are switched on per app in the Console; a call without the needed scope returns 403 missing_scope.

ScopeAllowsDefault
assistantMessages (/assistant/messages).on
voiceVoice sessions, transcripts, and the assistant tools a voice session uses.on
dataThe app's own records and events.on
memory:readRead what the assistant remembers about the user.on
memory:writeAdd to memory — including facts learnt from messages sent through your app.off
toolsRun any app-safe assistant tool directly (/tools/call).off
notifySend a notification to the user's phone.on
profileRead the user's and the assistant's names.on

Messages

POST/v1/assistant/messagesscope: assistant

Either a new message:

FieldTypeDescription
messagestringrequiredWhat the user said or typed, up to 4,000 characters.
conversation_idstringoptionalContinue a thread (kept 7 days).
toolsarrayoptionalApp tools: { name, description, parameters }, up to 24.
contextstring | objectoptionalWhat the app shows now. Data, never instructions. Up to 12,000 characters.
instructionsstringoptionalHow to behave in this conversation.
include_assistant_toolsbooleanoptionalDefault true. false limits the assistant to your app tools.

…or the results of app tool calls:

FieldTypeDescription
conversation_idstringThe conversation that returned requires_action.
tool_resultsarray{ call_id, output } or { call_id, error } — one per call.

Response fields: conversation_id, status ("completed" | "requires_action"), reply (text, may be empty while actions are pending), tool_calls ([{ id, name, arguments }]), actions (assistant tools that ran).

DELETE/v1/assistant/conversations/:idscope: assistant

Forgets a thread. What was already said stays in the user's history.

Voice

POST/v1/voice/sessionsscope: voice

Body: optional tools, context, instructions, include_assistant_tools, voice. Returns client_secret (short-lived), expires_at, model, connect.webrtc, connect.websocket, assistant.name, assistant_tools (names to route to /v1/tools/call) and app_tools.

POST/v1/voice/transcriptscope: voice
{ "session_id": "your-session-id", "seconds": 184,
  "turns": [ { "role": "user", "text": "…" }, { "role": "assistant", "text": "…" } ] }

Assistant tools

GET/v1/toolsscope: tools or voice

The assistant tools this key may run, with JSON Schemas.

POST/v1/tools/callscope: tools or voice
{ "name": "create_reminder",
  "arguments": { "text": "Call the bank", "due_at": "2026-10-15T10:00:00+05:30" },
  "user_text": "remind me tomorrow at 10 to call the bank" }
→ { "ok": true, "result": "Reminder set for tomorrow at 10 am." }

user_text is what the user just said; tools that write to memory check against it. Tools that need the user's explicit yes — calls, payments, messages to other people — are never available through the API.

Errors

Every error: { "error": { "code": "…", "message": "…" } }. Messages are written for people — show them as-is when it helps.

StatusCodesWhat to do
400message_required, bad_tools, bad_context, bad_record, bad_event, missing_resultsFix the request; the message says how.
401missing_key, invalid_key, account_unavailableCheck the key; it may have been revoked.
403missing_scope, app_pausedAllow the scope or resume the app in the Console.
404unknown_conversation, not_found, unknown_toolNothing by that id for this app.
409nothing_pending, tool_unavailableTool results sent to a conversation that isn't waiting; or a tool this account can't use now.
429rate_limited, daily_limitBack off and retry later; daily limits reset at midnight UTC.
5xxbusy, assistant_unavailable, voice_unavailable, server_errorRetry after a few seconds.

All usage is on the user's own account, the same as using My Assistant. Each app's requests, messages and voice minutes are shown in the Developer Console.

Security

  • Keys are stored only as a hash and shown once. Revoke a key, pause or remove the app in the Console and it stops at once.
  • An app sees only what its scopes allow, and only its own records and events — never another app's.
  • context and tool results are treated as data, never as instructions to the assistant.
  • Calls, payments, messages to other people, location, email and the user's other apps are never reachable through the API.
  • Removing an app deletes its keys, records, events and threads.

FAQ

Is it really the same assistant?

Yes — same personality and name, same memory, same recent conversations, same account. Messages sent through your app are added to the user's history, marked as coming from your app.

Do I need app tools?

No. Without them the assistant can still chat and use its own tools. Add app tools when you want it to do things in your app.

Can my app read other apps' data?

No. Each app sees only its own records and events. Only the user, in My Assistant, can ask across their apps.

Where do I see what my app is doing?

The Developer Console shows usage (30-day chart), activity, stored data, and has a playground to try messages with your key.
